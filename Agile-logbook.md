## Agile Logbook
Log entry 1: Project initiation and problem definition

Activities completed

Identified university students as the primary community.
Defined the problem of unreliable or unaffordable laptops.
Discussed the risks associated with travelling to unfamiliar repair locations.
Developed the initial PC Revival business idea.

Evidence

Initial entrepreneurship document.
Problem statement.
Group role allocation.
Survey-planning evidence.

Reflection

This activity helped me understand that the project needed to solve a clearly defined community problem. The proposed solution became stronger when it was connected to interrupted academic work, affordability and access to trustworthy services.

Log entry 2: Survey and requirements gathering

Activities completed

Designed and distributed questions relating to laptop usage, repairs and refurbished-laptop purchasing.
Collected 22 responses.
Reviewed the results to identify common needs.
Used the findings to inform the proposed services.

Evidence<br>

[Survey link](https://docs.google.com/forms/d/1vqk1VHflU8mbcyBA2tnYXLf5IP63G9PogJuAFLV2AYw/edit#responses)

The supplied survey artefacts report that 17 of 22 respondents selected attending online classes, 12 selected programming or coding, and 11 selected writing or reading tasks. The survey also shows 45.5% answering that they had experienced a laptop needing repair. For refurbished laptops, 50% selected yes and 31.8% selected maybe.

Reflection

The survey prevented the project from relying entirely on assumptions. I learned that requirements are stronger when they can be traced to evidence. I would improve future surveys by including more open-ended questions and by recruiting a broader group of respondents.

Log entry 3: Team Charter and planning

Activities completed

Defined team values.
Assigned responsibilities.
Agreed on communication tools.
Documented decision-making and conflict-resolution processes.
Identified project goals and success measures.

Evidence

Team Charter board.
Role list.
Trello workspace.
Communication records.

Reflection

The charter clarified how the team intended to work and what behaviour was expected. The process showed that responsibilities must be specific enough to support accountability. I also recognised that duplicated or unclear role assignments can create delays if ownership is not confirmed for each task.

Log entry 4: User stories and backlog creation

Activities completed

Converted requirements into user stories.
Added acceptance criteria.
Broke stories into implementation tasks.
Prioritised the product backlog.
Selected the first group of sprint items.

Evidence

Trello cards.
Product-backlog table.
Acceptance-criteria checklists.
Sprint-planning notes.

Reflection

This step connected the business idea to practical software work. I learned to keep the user’s need in the story and place the technical detail in the tasks. Acceptance criteria also created a clearer basis for testing.

Log entry 5: Interface design and navigation

Activities completed

Designed the main page structure.
Created navigation between portfolio or system pages.
Applied a consistent visual style.
Considered desktop and mobile presentation.
Connected project information to the relevant pages.

Evidence

Wireframes or early page captures.
Final navigation screenshots.
GitHub commits.
Before-and-after comparisons.

Reflection

Creating separate pages improved the organisation of the information, but navigation only added value when every link worked and every page had a clear purpose. I learned that interface design must support the user journey rather than only improving appearance.

Log entry 6: Data and feature integration

Activities completed

Connected customer-facing forms to project data.
Tested create and retrieval operations.
Added validation and feedback messages.
Checked that stored information could be displayed.
Recorded technical problems and corrections.

Evidence

Form screenshots.
Database records.
Test results.
GitHub commits.
Error and corrected-output evidence.

Reflection

Integration was more demanding than creating static pages because a problem could exist in the user interface, configuration, database or communication between components. I learned to test one operation at a time and use the returned error information to locate the actual cause.

Log entry 7: Testing and quality improvement

Activities completed

Tested navigation.
Checked important forms.
Tested valid and invalid input.
Reviewed layout on different screen sizes.
Corrected critical defects.
Compared completed work with acceptance criteria.

Evidence

Test table.
Screenshots of test results.
Issue list.
Fixed GitHub commits.

Reflection

Testing showed that a feature is not complete merely because it works once under ideal conditions. The project also needed to respond appropriately to blank fields, invalid input and missing information. I would introduce testing earlier in future so that defects are corrected while the related code is still fresh.

Log entry 8: Portfolio preparation and deployment

Activities completed

Selected the strongest project artefacts.
Added evidence captions.
Connected evidence to learning.
Wrote reflections for each rubric category.
Reviewed spelling, links and navigation.
Prepared the GitHub Pages submission.

Evidence

Published portfolio.
Final commit history.
Page screenshots.
Link test.
Submission capture.

Reflection

Preparing the portfolio made me look at the whole project rather than only the final website. I learned that evidence must be selected and explained. A screenshot on its own does not prove what was learned unless its relationship to a requirement, decision or improvement is clearly stated.
