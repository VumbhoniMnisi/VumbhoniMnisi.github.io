## Sprint Backlog

### Sprint 1: Foundation and research
Sprint goal

Establish the project foundation and translate PC Revival’s business problem into an organised, navigable digital solution.

| Sprint item        | Planned activities                                              | Expected evidence     |
|--------------------|-----------------------------------------------------------------|-----------------------|
| Team Charter       | Finalise purpose, values, roles and working agreements          | Charter screenshot    |
| Requirements       | Review survey findings and define user needs                    | Requirements document |
| User stories       | Write initial stories and acceptance criteria                   | Trello cards          |
| Interface planning | Produce page structure, navigation and wireframes               | Design screenshots    |
| Project setup      | Configure repository and basic website structure                | GitHub commits        |
| Core pages         | Create home, about and services pages                           | Page screenshots      |

Sprint retrospective<br>
What went well: The project problem and target market were already supported by survey evidence.
What required improvement: Broad business ideas had to be converted into smaller technical requirements.
Improvement action: Add acceptance criteria and owners before moving a story into development.
### Sprint 2: Core customer functionality
Sprint goal

Provide working customer-facing functionality for repair requests, quotations and refurbished-laptop browsing.

| Sprint item       | Planned activities                                   | Expected evidence   |
|-------------------|------------------------------------------------------|---------------------|
| Repair request    | Build and validate the repair form                   | Form submission     |
| Data storage      | Store submitted repair requests                      | Database screenshot |
| Laptop catalogue  | Display refurbished-laptop information               | Catalogue page      |
| Laptop details    | Display product specifications and price             | Detail page         |
| Quotation request | Capture quotation enquiries                          | Submission evidence |
| Error handling    | Provide validation and clear messages                | Invalid-input tests |

Sprint retrospective
What went well: User stories gave development a clearer direction.
What required improvement: Data integration introduced more dependencies than static page design.
Improvement action: Test database operations as soon as each form is connected instead of waiting until the end of the sprint.

### Sprint Backlog reflection

The sprint backlog helped me understand the difference between all desired project work and the smaller set of work selected for immediate implementation. The product backlog represented the wider product vision, while the sprint backlog focused on the tasks needed to achieve a specific goal.

Breaking the project into foundation, core functionality and quality stages created a logical order. The page structure and requirements needed to be established before database-connected forms could be tested. Similarly, final deployment and evidence preparation depended on the main functions already being stable.

One lesson was that a sprint should not contain more work than the team can realistically complete. Work that is started but not tested cannot automatically be treated as finished. If I repeated the project, I would use the team’s actual delivery data to improve estimation and would move incomplete stories back into the product backlog rather than presenting them as completed.
